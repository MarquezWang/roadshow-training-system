# 登录页与账号体系方案

## 目标

为内部测试和后续上线增加基础访问控制，避免训练项目、录音、报告等内容在未登录状态下被访问。

## 第一阶段建议

- 增加登录页 `/login`。
- 使用服务端 session/cookie 保护核心页面。
- 先支持单个管理员账号或少量内部测试账号。
- 保护范围：
  - `/projects`
  - `/projects/new`
  - `/projects/[id]`
  - `/training/[sessionId]/**`
- 暂不做复杂组织、团队、邀请、权限分层。

## 账号数据

第一阶段有两种低风险方案：

1. 环境变量账号
   - 适合内部测试。
   - 不改数据库 schema。
   - 示例：
     - `ADMIN_USERNAME`
     - `ADMIN_PASSWORD_HASH`

2. 数据库 User 表
   - 适合准备正式上线。
   - 需要 Prisma schema 和 migration。
   - 后续可支持项目归属、多人协作、权限分级。

当前建议先用环境变量账号，确认产品流程后再升级数据库账号体系。

## 登录交互

- 登录页保持简洁：
  - 系统名称
  - 用户名
  - 密码
  - 登录按钮
  - 失败提示
- 登录成功后跳转到 `/projects`。
- 未登录访问受保护页面时，跳转到 `/login?next=原路径`。
- 已登录访问 `/login` 时，自动跳转到 `/projects`。

## 安全要求

- 不在前端暴露密码或 hash。
- 密码校验放在服务端。
- cookie 使用 `httpOnly`。
- 生产环境使用 `secure` cookie。
- 登录失败提示保持模糊，例如“账号或密码不正确”。
- 后续可增加登录失败次数限制。

## 后续增强

- 用户注册或邀请。
- 项目归属到用户。
- 管理员后台。
- 角色权限：管理员、普通用户、观察者。
- 微信或手机号登录。
- 登录审计日志。

## 回滚方案

如果登录页影响内部测试，可以通过环境变量关闭访问保护，例如：

```env
AUTH_ENABLED=false
```

关闭后恢复当前无登录访问模式。
